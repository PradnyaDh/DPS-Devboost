Data defect DevBoost score Code coverage metric 17 Sep 2026

Code coverage is scored 100× too low

The coverage metric is worth 5 of the 100 DevBoost points. Because it is normalized against a maximum of 100 while the underlying value is a fraction, no team has ever earned more than 0.05 of those 5 points — including teams at 94% coverage.

All 11 verticals affected · 328 teams · 3.15 points lost on average · 170 of 198 squads company-wide change rank once corrected

The loss is not uniform. It scales with coverage, so the teams with the best test suites are penalized hardest — including Tech Foundations, who own the metric. The official Looker Studio report reads the same column, so it shows the same wrong score.

01

The two numbers disagree by exactly 100

Every row of the score table stores both a raw measurement and the normalized 0–1 credit derived from it. For coverage, dividing one by the other gives the same answer on every row ever published — all 19 months, every vertical, no exceptions.

rows4,916 real measurements · 19 months · Mar 2025 – Sep 2026
minraw ÷ normalized = 100.000000
maxraw ÷ normalized = 100.000000
outliers0 rows deviate by more than one-millionth
spreadzero — not an approximation, a constant

A constant factor of exactly 100 across every row is the signature of a unit error, not of noise or a rounding artifact. The documented formula is min–max normalization with bounds 0% → 100%; the raw value arrives as a fraction where 0.82 means 82%. Dividing by 100 rather than by 1 is the whole defect.

02

Coverage caps at 1% of its credit; every other metric reaches 100%

This is the control that rules out a misreading of the scale. If coverage were simply stored differently, its normalized ceiling would still be 1.0 like its peers. It is not.

05

The penalty grows with the quality of the test suite

Because the awarded credit is pinned near zero regardless of input, a team's loss equals its actual coverage. The metric therefore does the opposite of what it was designed to do: the better a team's tests, the more score it forfeits.

80–100%−4.34
50–79%−3.50
20–49%−1.88
under 20%−0.38

Average points lost of 5 available, by coverage band, across all 328 teams with a coverage measurement in August 2026 — 102 teams sit in the top band. A team with no tests at all loses almost nothing, because it had almost nothing to be credited for.

Two orgs are unaffected because their squads' coverage happens to be tightly clustered — where coverage varies within a group, the ranking shifts. Company-wide comparison is where the distortion is largest, because that is where coverage varies most.

So the defect is not cosmetic deflation. Any conversation that compares one team against another on DevBoost score is using a ranking the correct arithmetic would reorder — and cross-org comparisons, where coverage varies most, are the ones most affected.

07

The official report inherits it — there is no correct view

It would be reassuring if the Looker Studio report computed its own, correct score. It does not. Loading it for one tribe and comparing against the table settles which value it uses.

team[TRIBE] Logistics / Rider / Deliveries · Sep 2026
reportCode Coverage 82.49% · DevBoost Score 60%
tablescore with broken credit = 60.50
tablescore with correct credit = 64.58
verdictthe report's score matches the broken value, not the corrected one

The report displays the raw coverage correctly — 82.49% is the fraction 0.8249 rendered as a percentage. But its score field reads overall_score straight from the same table, so it carries the same 100× error. Every consumer of this metric inherits one upstream normalization fault; there is no second system holding a correct answer to defer to.

What would settle it

  1. Confirm the intended bound for coverage in the scoring config — the methodology page states 0% → 100%, and the raw column stores a fraction, so the maximum should be 1, not 100.
  2. Note that fixing the table fixes every consumer at once — the Looker Studio report reads overall_score from it directly, so there is no second place to correct and no disagreement to reconcile.
  3. If the table is wrong, a backfill would shift historical scores upward by up to 4.9 points and reorder team comparisons — worth flagging before anyone reads a trend across the fix.
  4. Worth knowing either way: the defect is company-wide, so it is not a question any single vertical can answer for itself.
